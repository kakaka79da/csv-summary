# "길드 오피스" → 판매 가능한 멀티테넌트 SaaS — 검토 및 제안

이 문서는 "나도 쓰고 판매도 가능한 시스템"으로 확장하고 싶다는 요청에 대한 검토·제안·
로드맵·예산 추정을 정리한다. 결론부터: **지금 이 저장소는 프로토타입(브라우저 하나,
백엔드 없음)이고, 요청하신 제품은 실제 멀티테넌트 SaaS다. 이 둘 사이의 간극이
이번 검토에서 가장 먼저 짚어야 할 지점이다.**

---

## 1. 요청 원문 요약 (의도 정리)

> 고객(대표)이 사업을 운영하며 AI 를 함께 쓰고 직원을 관리한다. 구글 드라이브나
> 개인 서버로 보안·용량 문제를 해결한다. 카카오워크/네이버웍스/슬랙 같은 업무
> 채팅 + 타임라인이 있는 테이블(노션) + 옵시디언(지식 그래프)을 한 화면에서
> 본다. UI 에서 직원 출퇴근/재택을 확인하고, AI 에게 시킨 일과 본인이 직접
> 입력한 일로 업무 파악을 한다. 문서 보고는 HTML 기반, 이메일로는 워드/엑셀 등
> 다양한 형식으로도 받을 수 있다. 채팅은 1:1 · 부서 단체 · 전사 공용 구조이며,
> 부서 채팅방은 AI·대표·사원 누구든 초대해서 만들 수 있다. 제작자 본인이
> `mkang428428@@` 시뮬레이션 모드로 먼저 테스트하며 점검·보완한다. 예상 제작
> 예산과 서버 운영 비용도 알고 싶다.

즉 목표는 **"AI+인간 혼합 팀을 위한, 통신+업무추적+지식베이스+근태를 한 제품에
담은 협업 툴"**이고, 지금 이 프로젝트를 그 제품의 **UX 참조 구현이자 최초
고객사(본인 회사) 겸 개발용 샌드박스**로 쓰겠다는 것이다.

## 2. 핵심 문제점 — 반드시 짚어야 할 것

### 2.1 구조적 간극: "브라우저 하나" vs "여러 회사"
지금 상태는 `zustand` + `localStorage` 뿐이다. 서버·DB·실시간 동기화·다중 사용자
격리가 전혀 없다. **판매 가능한 제품은 회사(tenant)마다 데이터가 분리되고,
여러 사람이 동시에 같은 회사에 로그인해 같은 화면을 봐야 한다** — 지금 구조로는
근본적으로 불가능하다. 이건 "기능을 더 넣는" 문제가 아니라 **완전히 새로운
백엔드를 세우는 문제**다. 지금 프론트엔드는 상태 머신(`agentMachine.ts`,
`missionMachine.ts`)과 UI/UX 는 재사용할 수 있지만, 저장소·인증·실시간 계층은
전부 새로 만들어야 한다 (`docs/BACKEND-MIGRATION.md` 참고).

### 2.2 "구글 드라이브 + 개인 서버" 둘 다 지원 = 스토리지 어댑터 계층
좋은 방향이다(플랫폼이 대용량 파일을 직접 들고 있지 않아도 되므로 비용·용량
문제를 고객에게 위임한다). 다만 "구글 드라이브"와 "개인 서버(S3 호환, WebDAV,
NAS 등)"는 인증 방식·API·에러 처리가 전혀 다르다. **처음부터 둘 다 만들면
일정이 두 배로 늘어난다.** 구글 드라이브 OAuth 하나만 먼저 만들고, "개인
서버(S3 호환 커스텀 엔드포인트)"는 어댑터 인터페이스만 설계해 두고 2단계로
미루는 걸 권한다.

### 2.3 "슬랙 + 노션 + 옵시디언을 한 화면에" 는 세 제품을 각각 다시 만드는 일
셋 다 수년간 전담 팀이 만든 제품이다. 문자 그대로 세 제품을 합치려 하면 범위가
끝없이 커진다. 제안: **이 셋이 실제로 해결하는 "일"이 뭔지로 되돌아가자.**
- 슬랙류 = 실시간 소통
- 노션류(테이블+타임라인) = 업무/일정 추적
- 옵시디언류(그래프) = 지식·관계 파악 → **이미 만든 관계도(`RelationshipGraph`)가 이 역할을 한다**

세 제품을 흉내내는 대신, **"AI+인간 팀 관리"라는 한 가지 목적에 맞춘 4개 화면**
(채팅 / 업무보드 / 근태·현황판 / 관계도)으로 압축하는 편이 실제로 다 만들 수
있는 범위이자, 더 차별화된 제품이 된다.

### 2.4 실시간 채팅 인프라가 없다
지금 `chats` 는 목업 데이터다. 실제 여러 사람이 실시간으로 대화하려면
WebSocket(또는 관리형 서비스: Pusher/Ably/Supabase Realtime)과 메시지 저장소가
필요하다. AI 직원이 대화에 참여하려면 실제 LLM API 호출도 붙어야 한다(이미
`BACKEND-MIGRATION.md` 에 "2단계 — 실제 AI 연결"로 정리돼 있다).

### 2.5 멀티테넌트 보안·법적 이슈
실제로 여러 회사의 데이터를 다루려면: 회사 간 데이터 격리(권한 실수 한 번이면
A사 데이터가 B사에 노출될 수 있다), 서버 측 감사 로그(클라이언트가 고칠 수 없는
append-only), 그리고 **개인정보보호법(PIPA)** — 근태, 급여, 사업자등록번호,
전화번호 등을 다루므로 개인정보처리방침·위탁 계약·보관기간 정책이 필요하다.
"인사관리 SaaS" 로 정식 판매하려면 이 부분은 변호사 자문을 권한다(내가 법률
자문을 대신할 수는 없다).

### 2.6 AI 사용량 = 원가 구조
AI 직원이 실제로 LLM 을 호출하면 그 비용은 플랫폼이 먼저 부담하고 고객에게
청구하는 구조가 된다. 지금 앱에 이미 있는 "회사별 월간 AI 예산" 개념을 그대로
**요금제의 근간**으로 쓸 수 있다 — 이건 잘 잡은 설계다. 다만 반드시 사용량
기반 과금이나 상한을 둬야 마진이 무너지지 않는다.

### 2.7 채팅방 자동 초대 권한
"AI 든 대표든 사원이든 초대 가능"은 유연하지만, AI 가 스스로 채팅방을 만들고
아무나 초대할 수 있게 하면 조직이 커질수록 방 난립·스팸 위험이 있다. 제안:
**AI 는 "이런 방을 만들고 이 사람들을 초대하는 게 어떨까요?" 라고 제안만 하고,
실제 생성은 대표/부서장이 승인**하는 구조(이미 이 앱 전체를 관통하는 "게임
연출 vs 실제 승인 게이트" 원칙과 맞는다).

## 3. 제안 아키텍처

### 3.1 제품 구조 (4개 핵심 화면)

| 화면 | 역할 | 지금 이 앱에서 이미 있는 것 |
|---|---|---|
| **채팅** | 1:1 · 부서 단체 · 전사 공용 | 1:1(`chats`)만 있음 → 부서/전사 채널 신규 필요 |
| **업무보드** | AI 지시 업무 + 사원 자기보고, 타임라인 | `MissionBoard` 있음, 타임라인 뷰·사원 자기보고는 신규 |
| **근태·현황판** | 출근/재택/미출근, 지금 뭐 하는 중인지 | `workMode`, `OfficeCanvas` 배치 있음 → 대시보드형 요약 뷰 필요 |
| **관계도** | 조직·프로젝트 관계 그래프 | `RelationshipGraph` 로 이미 구현됨 |

### 3.2 기술 아키텍처 (요약)

```
[브라우저]  React (지금 이 코드 재사용)
    │  WebSocket(실시간) + REST(그 외)
[백엔드]    인증 · 회사(tenant) 격리 · 채팅 저장 · 미션/승인 로직
    │           │                              │
[DB]      회사·직원·미션·채팅          [스토리지 어댑터]
                                     ├─ Google Drive OAuth (1단계)
                                     └─ 커스텀 S3/WebDAV (2단계, "개인 서버")
[AI 프록시]  회사별 예산·한도 검사 후 LLM API 호출 (Anthropic/OpenAI 등)
[이메일]     보고서를 워드/엑셀로 변환해 발송 (SendGrid/SES + 변환 라이브러리)
```

- 문서/보고는 화면에서는 계속 HTML(React) 로 렌더링하고, "내보내기" 시점에만
  서버가 워드(.docx)/엑셀(.xlsx)로 변환해 첨부 발송한다 — 지금 이미 CSV/마크다운
  내보내기가 있으므로 같은 패턴을 확장하면 된다.
- 채팅방 종류는 DB 에 `room(kind: 'dm' | 'team' | 'company_wide', department?)`
  로 모델링하고, 참여자 초대는 "제안(누구나) → 승인(대표/부서장)" 2단계로 둔다.

## 4. 단계별 로드맵

**0단계 — 지금 세션에서 바로 가능 (프론트엔드만, 여전히 시뮬레이션)** ✅ 완료
`mkang428428@@` 로 바로 테스트할 수 있다:
- ✅ 부서 단체 채팅방 + 전사 공용 채팅방(`ChatRoomsPanel`, 목업 데이터, 실시간 아님)
- ✅ 초대 흐름 — 대표가 부르면 즉시 확정, 사원이 제안하면 대표 승인 필요.
  "AI 가 초대"는 이 앱에 AI 자율 행동이 없어서, 대표가 초대할 때 어떤 AI 직원의
  추천으로 표시할지 직접 고르는 방식으로 구현했다(정직한 절충).
- ✅ 근태·현황판(`StatusDashboard`) — AI 직원은 실제 상태/진행 미션에서, 인간
  사원은 본인이 남긴 한 줄(`currentTaskNote`)에서 가져온다.
- ✅ 사원 자기보고 업무 입력 — 본인 기록만 수정 가능(대표가 대신 지어내지 않음).

다음으로 확인해볼 만한 것: 부서 채널이 실제 조직 구조와 맞는지, 초대
승인 흐름이 번거롭지 않은지, 현황판에 더 필요한 정보(예: 마감일, 우선순위)가
있는지 — `mkang428428@@` 로 직접 눌러보며 판단해달라.

**1단계 — 최소 백엔드 (인증 + 멀티테넌트 + 채팅 영속화)**
**2단계 — 실제 AI 연결 + 구글 드라이브 OAuth**
**3단계 — 부서 자동 채널, 타임라인/테이블 뷰, 개인 서버 스토리지 어댑터**
**4단계 — 판매 준비: 결제, 약관/개인정보처리방침, 감사 대응, 다중 관리자**

(1~4단계의 구체 항목은 `docs/BACKEND-MIGRATION.md` 의 표·API 설계를 그대로
확장해서 쓴다.)

## 6. 진행 방식 제안

1. **지금 바로**: 0단계(부서/전사 채팅방, 초대 흐름, 근태 현황판, 사원 자기보고)를
   이 프로토타입 위에 만들어서 `mkang428428@@` 로 바로 테스트·피드백받는다 —
   여전히 브라우저 하나짜리 시뮬레이션이지만, "이 UX 가 맞는 방향인지"는 지금
   확인할 수 있다.
2. **0단계를 써보며** 부서 채널 구조, 초대 승인 흐름, 대시보드 레이아웃 같은
   제품 결정을 확정한다.
3. **결정이 서면** 1단계(실제 백엔드) 를 시작한다 — 이건 이 세션 하나로 끝낼 수
   있는 작업이 아니라, 별도의 다인 개발 프로젝트로 봐야 한다. 내가 API
   설계·DB 스키마·인증 흐름 같은 설계 문서는 계속 도와줄 수 있고, 실제 서버
   코드도 (별도 백엔드 저장소가 생기면) 함께 작성할 수 있다.

이 문서는 계속 갱신하며 쓰는 걸 권한다 — 결정이 바뀔 때마다 이 파일에 반영하면
"왜 이렇게 만들었는지"의 기록이 남는다.
