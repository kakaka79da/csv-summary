# 보안 — 현재 한계와 개선 방법

이 프로토타입은 **프론트엔드 전용**입니다. 화면 흐름과 규칙을 검증하기 위한 것이며,
그대로 서비스에 올리면 안 됩니다. 아래는 지금 상태의 정확한 한계와 해결 방법입니다.

---

## 1. 지금 코드가 **하지 않는** 것 (의도된 안전장치)

| 항목 | 상태 |
|---|---|
| 공용 마스터 암호 | 존재하지 않음. 어떤 암호도 코드에 없음 |
| 프론트엔드에 저장된 관리자 암호 | 존재하지 않음. 로그인 화면에 암호 입력란 자체가 없음 |
| Git에 포함된 실제 `.env` | `.gitignore` 로 차단. `.env.example` 에는 변수 **이름과 형식만** 기록 |
| LocalStorage의 API 키 | 저장하지 않음. 키를 입력받는 UI 자체가 없음 |
| 하드코딩된 결제/인증 토큰 | 없음 |

API 연결 마법사(`ApiWizard.tsx`)의 3단계는 **키 입력란이 아니라 안내 화면**입니다.
연결이 완료되면 상태에 남는 것은 두 가지뿐입니다.

```ts
keyRef:    "srv-keyref://anthropic/emp_engineer"   // 서버가 발급한 참조 ID
maskedKey: "an-…••••4821"                          // 화면 표시용 문자열
```

`src/state/store.test.ts` 에 이를 지키는 테스트가 있습니다 — 상태 전체를 직렬화해도
`sk-` 로 시작하는 키 형태가 나타나지 않아야 통과합니다.

## 2. 지금 상태의 실제 한계

| # | 한계 | 위험 | 해결 |
|---|---|---|---|
| 1 | 인증이 없다 (역할별 데모 로그인) | 누구나 대표 권한으로 진입 | 아래 §3 백엔드 인증 |
| 2 | 상태가 `localStorage` 에 평문 저장 | 같은 브라우저를 쓰는 사람이 회사 정보·대화를 열람 | 서버 DB로 이전, 세션 쿠키 인증 |
| 3 | 비용 차단이 클라이언트에만 있다 | 개발자 도구로 상태를 고치면 한도 우회 가능 | 서버가 최종 게이트. 클라이언트 검사는 UX용 |
| 4 | 승인 게이트가 클라이언트에만 있다 | 승인 없이 호출 가능 | 승인 레코드를 서버에 두고, AI 호출 API가 승인 ID를 검증 |
| 5 | 감사 로그를 클라이언트가 보관 | 위·변조 가능 | 서버에 append-only 로 기록, 클라이언트는 읽기 전용 |
| 6 | AI 호출이 목(mock) | — | 서버 프록시로 대체 (§4) |

## 3. 관리자 최초 암호 — Bootstrap Password 방식

관리자 계정의 첫 암호가 필요할 때만 사용하며, **한 번 쓰고 폐기**합니다.

```
BOOTSTRAP_ADMIN_PASSWORD=replace-at-deployment   # 서버 환경변수에서만 읽는다
AUTH_SECRET=replace-at-deployment
```

절차:

1. 배포 시 환경변수로 임시 암호를 주입한다. **파일에도, 클라이언트 번들에도 넣지 않는다.**
2. 서버는 기동 시 관리자 계정이 없으면 이 값으로 최초 1회 로그인을 허용한다.
3. 최초 로그인 성공 즉시 **암호 변경 화면으로 강제 이동**한다. 다른 API는 잠근다.
4. 변경이 완료되면 부트스트랩 경로를 영구히 비활성화하고 임시 암호를 폐기한다.
5. 암호 **원문은 어디에도 저장하지 않는다.** Argon2id 로 해시해 저장한다.

```
argon2id, memoryCost ≥ 64MiB, timeCost ≥ 3, parallelism 1, salt 16B, 출력 32B
```

6. 로그인 실패 횟수를 제한한다 (예: 계정당 5회 실패 시 15분 잠금 + 지수 백오프).
7. 로그인·암호 변경·권한 변경·승인 결정은 모두 감사 로그에 남긴다.

부트스트랩 경로는 **최초 1회, 서버 로컬 네트워크에서만** 허용하는 것이 더 안전합니다.

## 4. API 키를 다루는 원칙

```
브라우저 ─(요청: keyRef + 작업 내용)─▶ 우리 서버 ─(실제 키 첨부)─▶ AI 제공자
   ▲                                        │
   └──────── 결과만 전달 ◀────────────────────┘
```

- 키는 **서버에만** 존재하고, 저장 시 KMS/Vault 로 봉투 암호화한다.
- 화면에는 마스킹 문자열만 노출한다 (`an-…••••4821`).
- 연결 해제와 키 교체 기능을 제공하고, 교체 시 이전 키를 즉시 폐기한다.
- 호출마다 사용량과 비용을 원장에 기록한다.
- **직원별 한도와 회사 예산 검사는 서버에서 수행한다.** 초과 시 호출 자체를 거부한다.
- 대표 승인이 필요한 작업은 승인 레코드 ID 없이는 호출이 거부되어야 한다.

---

## 5. 서버에서 반드시 다시 검사해야 하는 것

클라이언트의 검사는 사용자 경험을 위한 것이고, 실제 강제는 서버에서 합니다.

- [ ] 요청자가 그 직원에게 지시할 권한이 있는가
- [ ] 직원이 휴직 중이 아닌가
- [ ] 해당 도구가 그 직원에게 허용되어 있는가
- [ ] 접근하려는 데이터가 허용 범위 안인가
- [ ] 작업당 / 월간 / 회사 예산 한도를 넘지 않는가
- [ ] 승인이 필요한 종류라면 유효한 승인 레코드가 있는가
- [ ] 외부 발송(메일·웹훅)인 경우 승인자와 발송 대상이 기록되었는가

---

## 6. 배포 전 점검

- [ ] `.env` 가 저장소에 없는가 (`git log -p | grep -i 'sk-'` 로 과거 커밋도 확인)
- [ ] 번들에 비밀값이 없는가 (`grep -R "sk-" dist/`)
- [ ] `VITE_` 접두사 환경변수에 비밀값을 넣지 않았는가 — **이 값들은 번들에 그대로 들어간다**
- [ ] CSP, HTTPS, 쿠키 `Secure`/`HttpOnly`/`SameSite` 설정
- [ ] 감사 로그가 서버에 남는가
- [ ] 관리자 부트스트랩 경로가 비활성화되었는가
