# 관리자 모드 · 회사 창립 승인 · 대표-관리자 메시지 — 스펙

이 문서는 "길드 오피스" 플랫폼 관리자 기능의 요구사항과 구현 방식을 정리한다. 대화로
전달된 요청을 그대로 프롬프트 형태로 남겨 재사용할 수 있게 하고, 실제 구현이 그
요청을 어떻게 (그리고 어떤 부분을 데모로 축소해서) 만족하는지 함께 기록한다.

---

## 1. 요청 원문 (요약 정리)

> 플랫폼 관리자는 "mkang" 표기를 누르고 숨은 코드를 입력하면 관리자 페이지로
> 들어간다. 관리자 페이지는 회사 삭제 승인, 회사 창립 신청 승인 등 "절대적으로
> 확인이 필요한" 항목을 처리하는 곳이다. 대표는 초기 로그인 후 회사를 창설하고,
> 가입 내역과 회사 코드 발급이 이루어진다. 직원은 회사 코드를 입력해 로그인/가입하고,
> 회사 코드를 가진 대표가 승인하면 그때부터 로그인할 수 있다 — 캐릭터 선택도 가입
> 시점에 함께 정한다.
>
> 관리자 페이지에서는 대표가 회사를 삭제할 때 반드시 관리자(시스템 관리자)가
> 승인해야 삭제된다. 회사 대표는 회사명·가입 아이디/비밀번호·사업자등록번호·휴대폰
> 번호·메일 주소를 입력하고 사업자 등록증 사본을 업로드(구글 드라이브에 저장)하면
> 관리자가 확인 후 승인한다. 관리자 페이지는 절대 권력을 가지며, 보안 관리와 회사
> 요청·건의 사항에 대응하는 메시지(채팅)창이 있어야 한다 — 회사 대표마다 메시지를
> 보내면 관리자가 확인하고 피드백을 줄 수 있어야 한다. 회사를 새로 만들 때 기존
> 데이터는 따로 저장되어야 한다.

## 2. 진입점 · 역할

| 역할 | 로그인 방법 | 비고 |
|---|---|---|
| 대표 (CEO) | 로그인 화면의 "회사 대표 (CEO)" 버튼 | 회사가 없으면 창립 신청 화면으로 이동 |
| 인간 사원 | 로그인 화면의 "인간 직원" → 이메일 확인 → 회사 코드로 가입 신청 | 대표 승인 필요 |
| 플랫폼 관리자 | 로그인 화면에 **버튼이 없다.** 하단의 "플랫폼 제작: mkang" 표기를 클릭 → 코드 입력 | 아래 3절 참고 |

로그인 화면에는 관리자용 버튼을 전혀 노출하지 않는다 (`LoginScreen.tsx`).

### 3. 숨은 코드 세 개

같은 "mkang" 진입점(`EasterEggCredit.tsx`)에서 입력하는 코드에 따라 서로 다른 동작이
일어난다 (`store.tryEasterEggCode`, `data/easterEgg.ts`). 셋 다 문자열이 다르므로
서로 간섭하지 않는다.

| 입력 코드 | 동작 | 누가, 언제 쓰나 |
|---|---|---|
| `mkang428428` | "탱크형 변형 휠" 프로젝트의 **자동 재생 20분 시나리오**가 시작된다. 대표가 아무것도 누르지 않아도 AI 직원이 스스로 진행한다. | 사업자(대표)가 제품이 어떻게 동작하는지 **시연·확인**할 때 — "가상 테스트 모드" |
| `mkang428428##` | 세션이 없으면 **플랫폼 관리자**로 로그인해 `AdminDashboard` 로 이동한다. | 관리자가 회사 창립/삭제 승인 등 운영 업무를 처리할 때 |
| `mkang428428@@` | **관리자 승인·회사 신청 절차를 건너뛰고** 임의의 사업자(대표)로 즉시 로그인한다. 회사와 AI 직원 3명이 곧바로 준비되지만, 자동 대본은 재생되지 않는다 — 직접 눌러보며 자유롭게 기능을 테스트하는 용도. | 개발자/QA 가 실제 로그인 절차 없이 **여러 기능을 자유롭게 테스트**할 때 — "시뮬레이션 모드" |

`mkang428428` 과 `mkang428428@@` 은 목적이 다르다는 점이 핵심이다: 앞의 것은
**보여주기 위한 자동 시나리오**이고, 뒤의 것은 **직접 조작하는 자유 테스트**다.
시뮬레이션 모드로 들어간 회사는 헤더에 "🧪 시뮬레이션 모드" 배지로 계속 표시되어
실제 서비스 데이터가 아님을 알린다 (`WorldState.simulationMode`, 새로고침 시
초기화되는 비영속 값).

관리자 모드로 들어가면 오피스 화면(`OfficeScreen`)을 전혀 거치지 않고 곧바로
`AdminDashboard` 로 라우팅된다(`App.tsx`) — `phase` 값과 무관하게 동작해야 하므로,
`company` 가 없어도(삭제된 뒤에도) 관리자 페이지는 정상적으로 열린다.

## 4. 회사 창립 — 신청 → 관리자 승인

기존에는 대표가 창립 폼을 제출하면 즉시 회사가 만들어졌다. 이제는 **신청 →
관리자 승인** 2단계로 바뀌었다.

### 4.1 흐름

```
대표 로그인 (회사 없음)
  → "회사 창립 신청" 폼 작성 (FoundingFlow.tsx: CompanyApplicationForm)
  → submitCompanyApplication()  — CompanyApplication(status: pending) 생성
  → 대표는 "심사 중" 화면을 본다 (ApplicationStatusView)
  ...
  → 관리자가 mkang 코드로 로그인
  → AdminDashboard 에서 신청 카드 확인 (회사 정보 · 가입 아이디 · 사업자 서류 메타데이터)
  → decideCompanyApplication(id, 'approved' | 'rejected', note?)
       승인 시: 실제 Company 생성 (코드 자동 발급), companyApplications[id].status='approved'
       거절 시: companyApplications[id].status='rejected' (메모 포함), 회사는 만들어지지 않음
  → 대표가 다시 로그인하면 loginDemo() 가 "회사는 있지만 AI 직원이 없음"을 감지해
    사무실 건설(office_build) 단계부터 이어서 보여준다 — 창립 튜토리얼 연출을 그대로 유지
```

### 4.2 폼 입력 항목

- 회사명 / 대표자명 / 대표 캐릭터명 / 국가 / 지사 / 통화 / 월간 AI 예산
- 대표 전화번호 · 사업자등록번호 · 대표 이메일 (사업자 개업 시 필수)
- **가입 아이디** — 데모에서 신청 내역을 다시 조회하기 위한 식별자
- 대표 성별 + 캐릭터 외형 (남/여 캐릭터 선택 가능)
- 사업자 등록증 사본 (선택, 파일 메타데이터만 기록)

### 4.3 회사 코드

승인 시 `generateCompanyCode()` 로 자동 발급된다 (`Company.code`). 대표가 직접
입력하지 않는다. 직원은 가입할 때 이 코드를 입력한다.

## 5. 인간 사원 가입 · 승인 (기존 기능, 재확인)

- 사원은 이메일 확인 → (신규면) 이름·이메일(필수)·전화번호(선택)·회사 코드·희망 직무 +
  **캐릭터 외형(5종 중 선택)** 을 입력해 신청한다 (`StaffSignIn.tsx`,
  `applyAsHumanStaff`).
- 대표가 조직 패널에서 승인/거절한다 (`decideHumanStaffApplication`) — 관리자는
  관여하지 않는다.
- 승인 전에는 로그인해도 "처리중" 대기 화면만 보인다 (`StaffPendingScreen`).
- 대표는 재직 중인 사원을 즉시 내보내거나(`removeHumanStaff`) 다시 불러들일 수
  있다(`reinstateHumanStaff`) — 승인 절차 없이 대표 단독으로 처리한다.

## 6. 회사 삭제 — 관리자 승인 필수 (기존 기능 + 아카이브 추가)

- 대표가 삭제를 요청하면(`requestCompanyDeletion`) `Approval(kind:
  'company_deletion')` 이 생성된다. 대표 본인은 절대 승인할 수 없다.
- 관리자만 `AdminDashboard` 의 "회사 삭제 승인" 섹션에서 결정한다
  (`decideApproval`).
- **승인되면 데이터를 지우기 전에 요약을 아카이브에 남긴다** ("회사 생성 시 기존
  데이터는 따로 저장" 요청):

  ```ts
  ArchivedCompany {
    company            // 삭제 시점의 회사 정보 스냅샷
    archivedAt, reason
    employeeCount, humanStaffCount, missionCount, totalSpendUsd
  }
  ```

  전체 미션·대화·원장을 통째로 보관하지 않고 **요약 통계 + 회사 정보**만 남긴다 —
  브라우저 localStorage 용량과 개인정보 최소 보관 원칙을 함께 고려한 절충이다.
  상세 이력이 필요하면 감사 로그(`audit`)에 "회사 삭제 승인" 항목이 영구히 남는다.
- 회사 범위 데이터(직원·미션·사원·원장·대화 등)만 초기화되고, **관리자 세션은
  로그아웃되지 않는다** — 관리자 페이지가 `company` 유무와 무관하게 동작하도록
  바뀌었기 때문에 더 이상 로그아웃시킬 이유가 없다.

## 7. 대표 ↔ 관리자 메시지

- 대표는 설정 패널의 "플랫폼 관리자에게 문의"에서 메시지를 보낸다
  (`AdminMessageThread`, `sendPlatformMessage`).
- 관리자는 `AdminDashboard` 의 메시지함에서 회사별 스레드를 보고 답장한다.
- `threadKey` 는 회사가 생기기 전(신청 단계)에는 신청서 id, 생긴 뒤에는 회사
  코드를 쓴다 — 회사 코드가 곧 "이 회사와의 대화 채널 id"가 되는 셈이다.
- 대표·관리자만 메시지를 보낼 수 있다 (`sendPlatformMessage` 의 role 검사).

## 8. 데이터 모델 (신규)

`src/types/index.ts` 참고.

```ts
CompanyApplication {
  id, status: 'pending' | 'approved' | 'rejected'
  founding: Omit<Company, 'foundedAt' | 'code'>
  accountId: string                 // 데모용 식별자. 비밀번호 아님.
  documentRef: { fileName, sizeKb } | null
  submittedAt, decidedAt, decidedBy, note
}

PlatformMessage {
  id, threadKey, companyName
  from: 'ceo' | 'admin', authorName, text, ts
}

ArchivedCompany {
  id, company, archivedAt, reason
  employeeCount, humanStaffCount, missionCount, totalSpendUsd
}
```

`Session` 에 `companyApplicationId?: string | null` 이 추가되어, 대표가 신청서
심사 결과를 다시 로그인해서도 이어서 볼 수 있게 한다 (`humanStaffId` 와 동일한
패턴).

## 9. 반드시 지킨 보안 원칙 (이 프로토타입이 절대 하지 않는 것)

프로젝트 시작 시점에 정한 규칙을 이번 기능에도 그대로 적용했다:

1. **실제 비밀번호를 받지 않는다.** "가입 아이디"는 조회용 식별자일 뿐이며, 어떤
   비밀번호 필드도 폼에 없고 상태에도 저장하지 않는다.
2. **관리자 코드(`mkang428428##`)는 프론트엔드 상수다.** 데모 로그인 게이트일
   뿐 실제 인증이 아니다 — 실서비스에서는 서버 세션 기반 인증 + Argon2id 해시 +
   로그인 실패 제한으로 대체해야 한다 (`docs/SECURITY.md`).
3. **사업자 등록증 사본을 실제로 저장하지 않는다.** 파일 이름·용량 메타데이터만
   신청서에 기록한다. "구글 드라이브에 저장"은 서버가 사용자 대신 OAuth 토큰을
   들고 파일을 업로드해야 하는 백엔드 작업이며, 클라이언트 번들에 그 자격증명을
   넣는 것 자체가 보안 사고이므로 이 프로토타입 범위에서는 구현하지 않았다.
4. **단일 브라우저 = 단일 회사.** 서버가 없으므로 "다른 기기에서 관리자가
   승인"을 흉내 낼 수 없다 — 같은 브라우저 안에서 역할을 번갈아 로그인하는 방식
   으로 흐름을 시연한다 (사원 승인 흐름과 동일한 패턴).

## 10. 제안 — 추가로 고려할 수 있는 것

요청 마지막의 "다른 필요사항이 있다면 제안해줘"에 대한 답으로, 이번에 함께
구현하지는 않았지만 다음 단계에서 고려할 만한 항목:

- **관리자 코드 시도 제한 + 알림.** 지금은 몇 번을 틀려도 그냥 "코드가 올바르지
  않습니다"만 뜬다. 실제 서비스에서는 실패 횟수 제한과 감사 로그 경고가 필요하다.
- **다중 회사 지원.** 지금은 브라우저당 회사가 하나뿐이다. 실서비스에서는 관리자가
  여러 회사를 목록·검색·필터링할 수 있어야 한다.
- **관리자 결정 이력 CSV 내보내기.** 비용/미션/급여처럼, 승인·거절 이력도
  CSV로 뽑을 수 있으면 감사에 도움이 된다.
- **아카이브 복구 요청.** 지금은 삭제·아카이브가 되돌릴 수 없다. 유예 기간 동안
  대표가 "복구 요청"을 보낼 수 있게 하면 실수로 인한 삭제에 대비할 수 있다.
- **이메일/푸시 알림.** 신청 접수·승인·거절, 새 관리자 메시지 도착 시 실제
  알림을 보내는 것은 백엔드 항목이다.
- **다중 관리자 계정.** 지금은 관리자가 한 명(코드 하나)이라고 가정한다. 실제로는
  관리자별 계정과 `decidedBy` 이력(이미 기록 중)을 바탕으로 책임 소재를 구분해야
  한다.
